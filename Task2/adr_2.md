# ADR-2: Проработка высокоуровневого видения решений

## 1. Контекст
При заданной архитектуре (см. ADR-1), необходимо сформировать ограниченные контексты, которые позволят спроектировать конкретные микросервисы

## 3. Решение

1) **Cервис мониторинга поведения животных**.
 В рамках данного сервиса будет осуществляться  мониторинг поведения животных. Сервис будет
 получить поток видеоданных от  какой-то камеры и анализировать поведение животных. Отслеживание тревожного поведения  и состояния животных -- драки, задавливание. В общем, любую подозрительную активность или, наоборот, неактивность. В случае, если детектирвано какое-либо тревожное поведение, сервис должен оповещать о них. Для каждого типа определяемого поведения должны задаваться пороги\значения, чтобы уменьшить ложные срабатывания. Сервис должен быть отказоустойчивым(99,95%) и иметь высокую надежность.
 Сервис отправляет в брокер даные через LoRaWAN. Если по каким-то причинам соединение будет отсутстововать то использовать модем с сим-картой для отправки сообщений дежурному сотруднику. Для этих целей надо будет использоваться  отдельный сервис. Чтобы не потерять данные при отправке,
 все события перед отправкой записываются сначала в локальную бд (типа sqlite).


2) **Сервис мониторинга состояния и учета количества.**
 Данный сервис предназначен для выяления признаков болезни у животных и учета их количества.
 Данный  модуль сделан общим для 2х казалось бы не очень сходных задач -- мониторинг состояния и пересчет. С другой стороны, данные сервисы сходны по характеру работы -- периодически
 получать видео поток от камеры и анализировать его. Т.е. нет необходимости анализировать
 видеопоток в реальном времени, т.к. едва ли состояния животных будет часто меняться, равно как и их количество. Т.е. данные характеристики если меняются, то не очень часто. 
 Полученные в результате анализа данные сохраняются локально и\или передаются во вне.
 
 **Замечание**. В плане реализации данный сервис может быть либо объединен с сервисом мониторинга поведения, таким образом мы получим что-то вроде модульного монолита, либо может быть отдельным сервисом на том же edge устройстве. Более того, может быть имеет смысл данный сервис поставлять только с камерами типа "рыбий глаз" для наибольшего охвата всех животных, полностью отдельно от сервиса мониторинга поведения.

3) **Сервис мониторинга и управления  инфраструктурой, обеспечивающей жизнедеятельность животных -- поилки, корм.**
 Данный сервис отвечает за управление и контроль за инфраструкторой, необходимой для жизнедеятельности животных. Сервис отвечает за управление, настройку и контроль качества
 поилок и кормушек. В случае достижения каких-то тревожных значений, сервис должен оповещать персонал о соотв. проблеме. Сервис взаимодействует с IoT-шлюзом через LoRaWAN. При возникновении перебоев с интернетом, использовать отправку сообщений с помощью модема. Сервис должен быть отказоустойчивым(99,95%) и иметь высокую надежность.

4) **Сервис сбора и экспорта метрик.**
 Данный сервис должен предоставлять функционал для создания, сбора и экспорта необходимых метрик. Предполагается собирать как метрики с устройств -- всякие датчики на оборудовании и т.п. -- так и бизнес метрики (типа кол-во нездоровых особей или тревожных инцидентов за день или временной интервал), которые пользователи будут добавлять вручную, так и метрики работы ПО. Предполагается делать экспорт за определнный интервал в формате csv. Желательно использовать существующие решения типа Prometheus, TimescaleDb. Сервис должен работать как с базой временных рядов для сбора метрик с устройств, так и с хранилищем данных для сбора бизнес метрик.

5) **Cервис авторизации и аутентификации.**
При использовании моб. приложения или веб-портала данный сервис должен авторизовывать пользователя. В целом, можно заимствовать уже существующее решение от платформы "АгроТех Х".

6) **Сервис для надежной отправки  критичных сообщений.**
 Данный сервис будет работать с модемом с сим-картой для отправки критически важных сообщений дежурному сотруднику и\или в брокер. Севрис будет получат сообщения от соотв. сервисов по mqtt, после чего будет отправлять каким-либо образом, например sms, дежурному сотруднику. Сервис должен быть отказоустойчивым(99,95%) и иметь высокую надежность.
 Возможно, что как отдельный сервис его делать и не надо, а просто с каждым edge устройством поствлять еще и модем. Более того, если будут проблемы с Wifi, то не факт, что до данного сервиса получится достучатся, разве что прокладывать оптику до него.

 7-) Остальные сервисы типа iot-шлюза или хранилища данных будут расширяться по мере необходимости.
